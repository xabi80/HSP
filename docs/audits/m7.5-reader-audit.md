## 1. `floatsim/hydro/readers/capytaine.py`

**Current symmetry handling:** verified.

- `_extract_hydrostatic` at line 382:
  `sym = 0.5 * (perm_matrix + perm_matrix.T)` — explicitly

After Q1's HydroDatabase-level symmetrization lands, the

`0.5 * (0.5*(M+M.T) + 0.5*(M+M.T).T) = 0.5 * (M+M.T)`).

**Q2 finding — critical:** the reader has **zero mesh

- Imports only `numpy`, `xarray`, and `floatsim.hydro.database`

- Consumes only `xr.open_dataset(nc_path)`.

    FloatSim gains the ability to run Capytaine, not

    PR3's scope contracts: no reader changes, only new
    module + tests. The Terminal validation gate's
    workflow (α) description in the M7.5 plan already
    reads correctly under this interpretation (Pre-flight
    0 calls the utility on the raw GDF BEFORE running
    Capytaine).

Disposition (b) is correct and preserves Q2's intent. The
audit surfaces this before PR3 opens rather than at
implementation-time confusion.

## 2. `floatsim/hydro/readers/wamit.py`

**Reference symmetrization pattern:** verified.

`_resolve_6x6_from_dict` at line 550 (constant
`_SYM_RTOL = 1.0e-6` at line 85) averages duplicate
`(i, j)` / `(j, i)` entries at parse time. The docstring
(lines 555-575) explicitly documents the intent: "the
solver writes both halves of a physically symmetric
coupling, and panel-method noise produces small
asymmetries (typically far below the diagonal scale). For
example, marin_semi at T=12.57 s gives M[4,6]≈92 and
M[6,4]≈48 (port-starboard symmetry of the OC4 semi makes
both physically zero); the diagonal scale is ~8e6, so this
is solver noise, not a file bug."

Post-averaging, the matrix is **exactly symmetric by
construction** (`np.array_equal(M, M.T)` returns True at
float64 precision). The `HydroDatabase.__post_init__`
`_require_symmetric` check trivially passes.

**Q1 idempotency verification (deferred to PR2 Step B).**
The audit CANNOT byte-diff pre- vs post-Q1 change because
the Q1 change hasn't landed yet. The verification is
**expected to be a no-op** based on the following
reasoning:

- WAMIT reader output is bit-exactly symmetric
  (`M[i,j] == M[j,i]` down to the last bit).
- Q1's symmetrization step `0.5 * (M + M.T)` on a matrix
  that satisfies `M == M.T` produces a matrix bit-identical
  to `M` (there's no floating-point subtraction; the sum
  produces `2*M[i,j]` at each entry, and dividing by 2 in
  IEEE 754 is exact for finite values).
- Therefore the byte-diff PR2 asserts will produce zero
  differences.

PR2's Step B verification is the empirical confirmation.
Audit outcome: **expected no-op**, PR2 confirms empirically.

**Q1 tolerance tightening (rtol=1e-6 → rtol=1e-12):**
same reasoning — the WAMIT reader output is bit-exactly
symmetric, so `np.allclose(M, M.T, rtol=1e-12)` returns
True. The tolerance change is a no-op on the current WAMIT
fixture set.

**Callsite audit (`read_wamit`):** 12 test call sites
across `test_wamit_reader.py`, `test_excitation_wamit_convention.py`,
and validation tests; 1 dispatcher call. All use `stem`
positional + keyword kwargs; none depend on pre-Q1
tolerance semantics.

**Q2 finding:** none — the WAMIT reader operates on
`.1` / `.3` / `.hst` text files, not meshes.

**Q3 finding:** none.

**Baseline discovery — F2 hypothesis tolerance fix (`bbb5b9b`).**
The initial pytest baseline surfaced one deterministic
hypothesis property-test failure in
`tests/unit/test_connector_attachment_transform.py::test_property_F_ref_equals_T_pullback_of_F_attach`
(M7-Foundation PR2 code, `0d5f82f`). The shrunk falsifying
example was `r = [1e-8, 1e-8, 1e-8]` m with a small pure
rotation (`xi[3:6] = [3.125e-2]*3` rad, translation zero) and
a triangular SPD `K_attach` with entries 1..6. The observed
discrepancy at pitch index [4] was **1.87e-9 absolute**
(**4.29e-9 relative**), just barely exceeding the `rtol=atol=1e-9`
gate.

**Root cause.** F2's cached
`K_ref = T^T @ K_attach @ T` construction loses precision at
very small `r` due to `r`-dependent corrections (magnitude
`~1e-8 * ||K||`) folding into O(1)-magnitude `K_ref` diagonal
entries. Storing the sum as a float64 matrix loses the tiny
corrections at their relative precision level; they re-emerge
at reduced precision when `K_ref @ xi` is computed. The
equivalent on-the-fly path (`T @ xi` first, then
`K_attach @ result`, then `T^T @ result`) preserves the
`r`-corrections as small perturbations to O(1)-magnitude
vectors throughout the chain. Same algebra; two different
numerical trajectories. Full mechanism, deferred analytical
work, and estimated effort in Phase 2 tracker entry
[`F2-HYPOTHESIS-TOLERANCE-EMPIRICAL`](../phase2-followups.md#f2-hypothesis-tolerance-empirical--f2-cached-k_ref-precision-bound-is-empirical-not-analytical).

**Regime.** The failing regime (`|r| = √3 · 1e-8 m ≈ 17 nm`)
is 5+ orders of magnitude below any physical body attachment
offset. Real Phase-1 fixtures use offsets in the
`1e-3` to `1e0` m range; at `r = 1e-3` the discrepancy shrinks
proportionally to `~1e-19`, well below any tolerance the
suite gates against. F2's precision at physical `r` is
unaffected. M7-Foundation PR2's docstring at
`0d5f82f` explicitly anticipated this class of
empirical-tolerance failure ("rtol = 1e-9 (looser than the
identity-test 1e-12 to accommodate hypothesis-induced
floating-point noise in K @ T @ ... compositions)").

**Disposition.** `rtol=atol` loosened from `1e-9` to `1e-8`
at commit `bbb5b9b` (2026-07-01), giving one decade of margin
over the observed shrunk example. Test now passes; F2's
precision at physical `r ≥ 1e-3 m` is unaffected. Analytical
bound derivation, cache-skip investigation, and
hypothesis-strategy regime constraint deferred per tracker
entry `F2-HYPOTHESIS-TOLERANCE-EMPIRICAL`. This baseline
(audit doc `a14a1ef` parent = `bbb5b9b`) is the reference for
PR2's Step B byte-diff verification on `marin_semi_trimmed`.

**Process note.** `bbb5b9b` is a REFINEMENT of the
M7-Foundation PR2 empirical-tolerance choice, not a
scope-expansion fix into M7.5. It landed on main with light-
touch approval; the calibration for future scope-expansion
questions arising during pre-milestone work is that they
default to explicit balanced-decision framing rather than
fastest-unblock recommendations (see the M7.5 pre-milestone
audit session's Code report, STEP 4 self-reflection). This
process-side reinforcement does not affect `bbb5b9b`'s
technical merit; both `bbb5b9b` and this audit doc at
`a14a1ef` stand on main.
