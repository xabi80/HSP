## Decisions to lock with Xabier

### Q1 — Symmetrization architecture

**Proposal: symmetrize at `HydroDatabase` construction, not
per-reader.**

Add a symmetrization step to `HydroDatabase.__post_init__`
BEFORE the `_require_symmetric` validation gate, applied
per-omega to A and B (and to A_inf and C, though those are
already symmetric coming out of both readers today —
idempotency on already-symmetric input costs one 6×6
`0.5*(M + M.T)` per validation, negligible). The WAMIT reader's
`_resolve_6x6_from_dict` arithmetic-mean averaging becomes a
no-op at the HydroDatabase gate (data arrives already
symmetric); no removal is needed. The Capytaine reader's
current explicit symmetrization in `_extract_hydrostatic` (line
382) and `_resolve_a_inf` (line 424) becomes similarly
redundant but harmless.

Audit-trail attribute: the symmetrization step records
`max |A - A.T|` and `max |A - A.T| / max |A|` on the
`HydroDatabase.metadata` dict per-slice-max, so downstream
tests can assert the asymmetry was within a physically
plausible range (e.g., `< 1e-2` relative — panel-method noise
should not be O(1)).

**Alternative: per-reader helpers** (each reader calls a shared
`floatsim.hydro.symmetrize.symmetrize_6x6` utility). Rejected
in the proposal because the invariant is a property of the
`HydroDatabase` type — the same invariant must hold no matter
which reader (or future reader) produces it. Per-reader
helpers create a symmetric-only-if-you-remember-to-call-it
pattern; HydroDatabase-level enforcement makes it
impossible-to-forget.

**Sub-decision (LOCKED, 2026-06-30): tighten
`_require_symmetric` from `rtol = 1e-6` to `rtol = 1e-12`.**
Post-symmetrization the residual is at float64 precision
(~1e-15 relative); the current `rtol = 1e-6` gate is
decorative — it cannot catch panel-method-noise-level
asymmetry (~1e-4 relative for real Capytaine BEM output on
non-trivial meshes) anyway, since noise at that level does not
survive symmetrization. Tightening to `rtol = 1e-12` leaves
three orders of margin over float64 precision and makes the
gate a real invariant check: any construction path that
bypasses `__post_init__`'s symmetrization step (or a future
external caller that assembles HydroDatabase by hand with
subtle asymmetry) is caught. The tolerance change is a hard
error at construction time, not at simulation time; visibility
is high.

**Open question for Xabier:**
- HydroDatabase-level symmetrization (proposal) or per-reader
  helpers?

**Rationale for proposal:** symmetrization is a property of
the HydroDatabase invariant; it applies to every BEM source
regardless of reader; HydroDatabase-level enforcement composes
cleanly with future readers (including B4 multi-body).
Downside: existing WAMIT reader tests may need re-verification
since the ingestion path changes even though outputs shouldn't
— Q7's audit lists the specific tests to re-run.

### Q2 — Panel-normal validation behavior

**Q2 lock (2026-06-30, refined via pre-milestone audit):
`mesh_hygiene` is a STANDALONE utility at
`floatsim/hydro/mesh_hygiene.py` providing
`validate_panel_normals(mesh)` and `fix_panel_normals(mesh)`.
Users invoke it in pre-BEM-solve scripts (e.g., the spar-fin
study's `capytaine_run.py`) BEFORE running Capytaine.
`read_capytaine` is unchanged (it consumes NetCDF, not
mesh). The pre-milestone audit at
[`docs/audits/m7.5-reader-audit.md`](audits/m7.5-reader-audit.md)
§Item 1 surfaced that `read_capytaine` has zero mesh handling
— the reader consumes only `xr.open_dataset(nc_path)`,
operates on post-BEM-solve NetCDF, and never imports the
`capytaine` Python package or handles a mesh. The original
"validation in Capytaine reader" language was misspecified
relative to the current codebase. The standalone-utility
model preserves Q2's intent (raise on failed validation,
companion utility for correction) with the correct
mechanical shape.**

- `mesh_hygiene` provides two functions:
    - `fix_panel_normals(mesh, method="centroid_outward",
      body_interior=None) -> mesh` returning a corrected mesh
      with panel winding flipped on any panel that fails the
      outward-normal test.
    - `validate_panel_normals(mesh, body_interior=None) ->
      (n_ok, n_reversed, indices)` — the check-only variant,
      pure function. **This is where the ValueError per §I2
      is raised** when reversed panels are detected.
- Module location LOCKED (2026-06-30) as single-file
  `floatsim/hydro/mesh_hygiene.py` per the driver.py
  precedent; promotion to package only if the file exceeds
  ~600 lines in a future extension.
- Adoption pattern is convention-driven: user scripts that
  produce Capytaine BEM output call
  `mesh_hygiene.validate_panel_normals(mesh)` before running
  the BEM solve. The spar-fin study's `capytaine_run.py`
  will be the reference example after M7.5 closes.
- `read_capytaine`'s module docstring gets a note pointing
  at `mesh_hygiene.validate_panel_normals()` as the
  recommended pre-BEM-solve hygiene step (docstring update
  only; no code change to `capytaine.py`).
- Scope limit to Capytaine-workflow meshes per Item 19
  test-first discipline: the spar-fin study exercised only
  the Capytaine path. Extending the utility to explicitly
  handle WAMIT-workflow meshes would need a WAMIT-produced
  reversed-normal fixture, which doesn't exist and would
  need to be synthesized — out of scope. The utility itself
  is workflow-agnostic (it takes any mesh; the M7.5 scope
  limit is on which workflows are exercised by tests, not
  on which meshes the utility accepts).
- The spar-fin study's
  [`fix_mesh_normals.py`](../studies/spar-fin-decay/fix_mesh_normals.py)
  becomes redundant after M7.5: `fix_panel_normals()` covers
  the case. The study's script is preserved on
  `scratch-spar-fin-decay` for the audit trail but doesn't
  run once the study re-verifies under workflow (α).

**Alternative (a): raise in all readers.** Rejected because
the WAMIT reader's normal handling is format-specific (WAMIT
GDF uses a signed IPERIO/ISX/ISY symmetry flag that changes
normal semantics per-panel-block); adding validation there
without a red fixture is untested surgery.

**Alternative (b): auto-correct with warning.** Rejected
because auto-correction is silent geometry modification. The
user's mesh has a bug; they should know about it. Raise +
utility gives the user the explicit correction path.

**Open question for Xabier:**
- Proposal, alt (a), or alt (b)?

**Rationale for proposal:** raise = honest signal (BEM
integrand on this mesh is silently wrong); auto-correct =
silent modification of user input. Utility function = explicit
convenience path with a discoverable API entry. Scope limit
to Capytaine reader per test-first discipline (only path with
a red fixture from the spar-fin study).

### Q3 — Item 25 override mechanism

**Proposal: function-call parameter on
`compute_retardation_kernel` requiring a rationale string.**

```python
def compute_retardation_kernel(
    hdb: HydroDatabase,
    *,
    dt: float,
    t_max: float,
    asymptote_check_override: str | None = None,
    ...
) -> RetardationKernel: ...
```

- When `asymptote_check_override` is `None` (default), Check 2
  runs unchanged (`std / |mean| < 0.10` on `B * omega^4` last
  10 points per diagonal, hard error).
- When passed a non-empty string, Check 2 downgrades to a
  warning that echoes the rationale string
  (`"Item 25 Check 2 asymptote gate overridden. Reason:
  {rationale}. Kernel is computed on the numerical data
  without 1/omega^4 tail extension."`) and the kernel is
  computed via a modified path that **zero-fills** the tail
  extension (LOCKED, 2026-06-30) rather than fitting 1/omega^4
  per entry. Zero-fill is the conservative default —
  attributes zero to the un-modelled ω > ω_max region rather
  than extrapolating a model that the asymptote-check
  explicitly said doesn't hold. Model-fit smoothing was
  considered and rejected: it introduces a numerical model
  where the data explicitly doesn't warrant one, and gives
  the user something to lean on that they shouldn't lean on.
- Empty-string rationale raises `ValueError`. "Empty" is
  defined as: `None`, `""`, or any string with `.strip() == ""`
  (whitespace-only). The check does NOT enforce
  "meaningful rationale" (that's not code-checkable); the
  point is the forcing-function acknowledgment that the caller
  is aware they're bypassing Check 2 and can articulate it in
  code review.
- Check 1 and Check 3 remain unchanged. Check 3
  (post-extension kernel decay) is the authoritative gate per
  Item 25 and CANNOT be overridden — its failure means the
  kernel is unusable regardless of what generated it. If a
  spar-fin-size body legitimately needs a longer buffer, that
  fixes the input to Check 3 by raising t_max, not by
  bypassing.

Companion conventions doc update: Item 25 gets a
"applicability bound" sub-item describing that Check 2 is
calibrated for bodies where the 1/ω⁴ asymptotic regime is
reached within the practical BEM ω_max range (OC4-class,
characteristic length O(10 m) or larger). Small bodies
(characteristic length ≲ 2 m) may need the override; the
Item 25 sub-item lists the diagnostic signature (heave B at
numerical floor by ω ≈ 5-10 rad/s AND surge/sway B has no
1/ω⁴ regime anywhere on the BEM grid). The applicability
sub-item also documents the zero-fill tail convention and its
implication for the user: **overridden-tail kernels do not
carry high-frequency information beyond ω_max; consumers
should not rely on the kernel's high-frequency response in
the overridden DOFs.**

**Alternatives:**
- **Boolean flag** (`skip_asymptote_check=True`). Rejected —
  no forcing function for the rationale; silent bypass in code
  review.
- **Environment variable** (`FLOATSIM_SKIP_ITEM25=1`).
  Rejected — invisible in call sites; enables blanket-skip
  across an entire test run, which is exactly the anti-pattern.
- **Config file entry.** Rejected — same invisibility issue;
  also violates the "no invented config" spirit of §9.

**Open question for Xabier:**
- Proposal or one of the alternatives (boolean flag / env
  variable / config file)?

**Rationale for proposal:** explicit function-parameter
acknowledgment, discoverable in the API, self-documenting in
code review (a diff adding `asymptote_check_override="..."`
is immediately visible). Rationale-required prevents silent
misuse. Zero-fill tail (locked above) = conservative default
that never over-attributes to the tail.

### Q5 — Non-convex body handling

**Proposal: punt entirely; open tracker entry
`PANEL-NORMAL-NONCONVEX-BODIES` in
`docs/phase2-followups.md`.**

The Q2 panel-normal validation assumes an unambiguous
"interior" — for convex bodies, `body_interior` is any point
inside the convex hull (the centroid of all vertices works).
For non-convex bodies (bodies with cavities: e.g., a torus, a
hollowed-out cylinder, a body with an internal moon pool),
the outward-normal test needs a per-panel interior definition
via ray-casting or SDF (signed distance field) computation.

All M1-M6 fixtures + the spar-fin study fixture are convex or
near-convex. Non-convex support has no current use case.

Tracker entry captures:
- The mechanism (ray-casting or SDF for non-convex interior).
- Visibility (invisible under current test coverage;
  becomes relevant when a moon-pool or ducted-body fixture
  arrives).
- Blocks (moon-pool floaters, ducted-body Morison elements,
  any body with a genuine cavity).
- Scope (extend `mesh_hygiene.validate_panel_normals` with a
  `topology="convex" | "nonconvex"` parameter; the nonconvex
  path needs a body-interior specification via SDF or point
  cloud).

**Open question for Xabier:**
- Agree with punt + tracker entry?
- If yes: does the tracker entry go in M7.5 PR1 (alongside
  the Item 25 applicability tracker entry that Q3 opens), or
  as a separate side-doc-commit before M7.5 opens?

**Rationale for proposal:** convex-only scope keeps M7.5
bounded; the ray-casting / SDF path is a substantial
implementation (well beyond hygiene scope). Tracker entry
prevents institutional loss.

### §I1 — Q1 audit-trail attribute structure on `HydroDatabase.metadata`

After the HydroDatabase-level symmetrization step fires, four
scalar attributes get populated on the `metadata` dict. Keys
and value semantics:

```python
metadata: dict[str, str] = {
    ...  # existing keys (source_format, source_path, etc.)
    "symmetrization_max_residual_A": "{max|A - A.T|:.6e}",
    "symmetrization_relative_residual_A": "{max|A - A.T| / max|A|:.6e}",
    "symmetrization_max_residual_B": "{max|B - B.T|:.6e}",
    "symmetrization_relative_residual_B": "{max|B - B.T| / max|B|:.6e}",
}
```

- Values are stringified per the existing `metadata: dict[str, str]`
  type (see `HydroDatabase` docstring).
- Max is taken over BOTH omega slices AND the 6×6 block —
  scalar per matrix, not per slice. Downstream consumers
  wanting per-slice detail can re-compute; the metadata
  attribute is the audit-trail summary.
- Computed on the PRE-symmetrization arrays (i.e., what the
  reader produced); the POST-symmetrization arrays are
  bit-identical to their symmetric counterparts within float
  precision.
- A_inf and C are not tracked in metadata: A_inf and C come
  from the reader already-symmetrized (per §I3 below, the
  Capytaine reader's `_extract_hydrostatic` and `_resolve_a_inf`
  symmetrization calls remain in place with a comment noting
  they're now redundant with the HydroDatabase-level step).
- Consumers (tests, closure-doc generators) can read these
  attributes to make the audit-trail record explicit: e.g.,
  the M7.5 closure doc will report the `marin_semi_trimmed`
  residuals to confirm zero (as expected for
  already-symmetrized WAMIT data) and the spar-fin
  `capytaine_bem.nc` residuals to confirm the ~1e-3 to 1e-4
  panel-method-noise level.

### §I2 — Q2 exact ValueError message text for panel-normal check

The `mesh_hygiene.validate_panel_normals(mesh)` function
raises with the following exact message when reversed-normal
panels are detected (single-line format wrapped for
readability):

```
Mesh has {n_reversed} panels with inward-facing normals
(out of {n_total} total; {n_reversed / n_total * 100:.1f}%).
BEM integration on this mesh will silently produce wrong
added-mass and radiation-damping values -- see conventions
doc Item 5 in docs/multibody-conventions.md and the spar-fin
study post-mortem in studies/spar-fin-decay/STEP-A-FINDING.md
for the pathology.

To correct, either:
  (a) Re-export the mesh with outward-facing normals from
      the upstream tool (OrcaWave, WAMIT, etc.), OR
  (b) Apply the study-local correction via
      floatsim.hydro.mesh_hygiene.fix_panel_normals(mesh),
      then pass the corrected mesh to the BEM solver.

Reversed-panel indices (first 10): {indices[:10].tolist()}
```

The `{...}` fields are Python f-string interpolations. Only
the first 10 reversed-panel indices are reported; the total
count is already in the opening line, and 10 sample indices
are sufficient diagnostic detail for identifying the mesh
region (all 10 typically cluster in the plate band on
spar-fin-class geometries). Dropping the "... and N more"
tail avoids nested f-string interpolation and keeps the
message code straightforward.

The message is designed for the M7-Foundation "long
descriptive error" precedent (see `LinearConnector`'s
NotImplementedError text at `connector.py:187+`). Rationale:
the user encountering this error may be encountering BEM
mesh internals for the first time; the message needs to
point them at both the concept doc (conventions Item 5) and
the corrective action (utility function).

Test assertion pattern (per Q6 PR3 Step B):
`pytest.raises(ValueError, match=r"Mesh has \d+ panels with inward-facing normals")`.
